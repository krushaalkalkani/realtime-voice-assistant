Answers out loud in 1.8 s. Break any part, and it still answers.

A spoken mock-interview coach: it asks a question, listens to your answer, and gives short spoken feedback. Speech-to-text, the language model and text-to-speech all run locally and stream into each other. Every stage of every turn is timed, and every component can fail without freezing the conversation.

Why

Voice assistants are judged on one feeling: how long the silence lasts after you stop talking. Building one that works on a happy path is easy. Knowing where each millisecond goes, and what the assistant does when the speech recognizer hangs or the model server dies, is what makes it production work.

So the project is built around measurement. Every stage emits a typed, timestamped event; latency is decomposed per turn; optimizations are kept only when the benchmark says they help; and faults are injected on purpose to prove the assistant degrades instead of freezing.

How it works

  1. 1
    Stream the microphone

    The browser resamples mic audio to 16 kHz and sends 32 ms frames over a WebSocket, which stays open both ways so audio can flow in and out at the same time.

  2. 2
    Detect the end of the turn

    Silero VAD scores every frame for speech; 700 ms of silence ends your turn. Talking over the coach (barge-in) stops its audio instantly.

  3. 3
    Transcribe, think, speak, overlapped

    faster-whisper transcribes, Llama 3.2 (Ollama) streams the reply, and Piper starts speaking the first clause while the model is still writing the rest.

  4. 4
    Time everything

    Each stage emits an event with a timestamp and its position in the recorded audio. That gives a latency breakdown per turn, p50/p95 dashboards, and an exact replay of any session.

  5. 5
    Never hang

    Every stage has a time limit and a plan B: type instead of talk, a filler line plus a fallback model, text-only replies. Circuit breakers skip a component that just failed.

When things break

A fault-injection script breaks each component against the real models for one spoken turn, switches it off, and checks the next turn is normal again.

Fault injection results
FaultWhat you getResponse
Speech recognizer down / hung"Couldn't make that out" plus a text box0.1 / 5.8 s
Language model down"Give me a second", fallback model answers0.6 s
Language model hung or slowSame, after a 3 s limit3.5 s
Model freezes mid-replyKeeps and speaks the part already written4.7 s
Text-to-speech down / hungText-only reply, already streaming on screen0.5 s
Model server unreachable (real outage)A spoken "having trouble thinking" line0.7 s
You talk over the coachAudio stops after 0.4 s of your speech; you become the next turn0.4 s

Every scenario recovered on the next turn, and 8 turns of random faults all finished. Fault injection also caught a real bug: on a 16 GB Mac, Ollama keeps one model in memory, so the fallback evicted the main model and the two kept evicting each other. The fix checks whether the main model is loaded and waits for a reload instead of falling back again.

    Run it yourself

    Needs a Mac or Linux machine with uv and Ollama. Costs nothing; nothing leaves your machine.

    git clone https://github.com/krushaalkalkani/realtime-voice-assistant
cd realtime-voice-assistant && uv sync
ollama pull llama3.2:3b && ollama pull phi4-mini
uv run python -m piper.download_voices en_US-lessac-medium --data-dir models/piper
uv run uvicorn server.main:app --port 8010   # open http://localhost:8010
